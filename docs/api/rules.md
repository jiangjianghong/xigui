# 规则配置详解(`config/rules.yaml`)

> 本文档面向**业务/产品/审核同学**——目标是让你看完之后能:
> 1. 理解每一条规则在判什么、参数怎么调
> 2. 评估初始版本(R001-R005)是否贴合实际业务
> 3. 提出"哪里没覆盖到 / 哪里判得太严太松"的反馈
>
> 与开发同学共读时,可一起参考 `app/rules/` 下的实现。

---

## 1. 整体结构

`config/rules.yaml` 是**活配置**——保存即生效:

- **自动**:下一次 `/compare` 请求时,系统会基于文件 mtime 自动重新加载
- **手动**:`curl -X POST http://localhost:6549/admin/reload-rules`

文件根节点为 `rules:`,下面是若干条规则。每条规则的字段:

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `id` | ✅ | 规则唯一编号(如 `R001`),**上游调 `/compare` 时按这个 id 找规则** |
| `name` | ✅ | 中文规则名(用于日志、对外展示) |
| `type` | ✅ | 规则类型,决定走哪个比对实现(5 种之一,见 §2) |
| `description` | ⭕ | 规则描述,仅用于日志/文档,不影响判定 |
| `expected_field_names` | ⭕ | 预期的两个字段名(`[a 字段名, b 字段名]`)。**仅文档化,不做强校验** |
| `require_field_name` | ⭕ | bool。该规则下请求里的 `field_a.name`/`field_b.name` 是否必填(详见 §1.1) |
| `params` | 看类型 | 参数包,每种 `type` 含义不同(见 §2) |
| `prompt_template` | 看类型 | 仅 `semantic_*` 用,占位符 `{a_value}`、`{b_value}`,可选 `{a_name}`、`{b_name}`。**不要遗漏花括号转义**(YAML 里 JSON 大括号要写成 `{{...}}`) |

### 1.1 `require_field_name` 与字段名注入

接口请求里 `field_a` / `field_b` 各有 `name`(字段名)和 `value`(字段值):

```json
{ "field_a": {"name": "建设单位", "value": "贵州省XX建设有限公司"} }
```

- `value` **永远必填**(Pydantic 层校验,缺则 422)
- `name` **默认可省略**——绝大多数情况业务侧不用传

只有这两种情况会强制要求 `name` 必填:

| 触发方式 | 示例 |
| --- | --- |
| yaml 显式写 `require_field_name: true` | 见下方"显式开启" |
| `prompt_template` 里引用了 `{a_name}` 或 `{b_name}` | 见下方"自动推导" |

**未提供 name 时返 422**:`{"detail":"rule R004 要求 field_a.name 必填"}`

#### 显式开启

```yaml
- id: "R010"
  type: "exact_match"
  require_field_name: true   # 强制业务侧必须传 name
  ...
```

#### 自动推导(推荐用于语义规则)

`prompt_template` 引用 `{a_name}` / `{b_name}` 时,系统会自动 imply
`require_field_name=true`,无需在 yaml 重复写一遍:

```yaml
- id: "R004"
  type: "semantic_similar"
  prompt_template: |
    请判断字段"{a_name}"与字段"{b_name}"的两个值是否指向同一主体。
    A: {a_value}
    B: {b_value}
    ...
```

这样上游必须传 `field_a.name="建设单位"`,LLM 才能在 prompt 里看到上下文(知道在判什么字段),判定更准。

## 2. 5 种规则类型详解

> 思路:**能用 Python 直算就别调 LLM**。前 3 种是确定性,token 全 0、毫秒级返回;后 2 种走 LLM,有 token 成本。

### 2.1 `exact_match`——归一化后严格相等

**用途**:判定两个文本是否**完全相同**,但允许容忍一些"无意义差异"。

**参数 `params`**:

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `ignore_whitespace` | `true` | 删除所有空白(空格、Tab、换行) |
| `ignore_case` | `true` | 字母全部小写比较 |
| `full_to_half` | `true` | 全角字母/数字/标点 → 半角(NFKC) |

**判定流程**:`normalize(a)` 与 `normalize(b)` 是否**字符级别完全一致**。

**典型示例**(参数全开):

| a | b | 判定 |
| --- | --- | --- |
| `  2024-001 ` | `2024-001` | ✅ true(去空白后相等) |
| `ABC-123` | `abc-123` | ✅ true(忽略大小写) |
| `２０２４` | `2024` | ✅ true(全角转半角) |
| `项目X` | `项目Y` | ❌ false |

### 2.2 `numeric_equal`——抽取数值后按容差比较

**用途**:金额、面积、比例等数字字段,允许不同单位表达。

**参数**:

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `tolerance` | `0.0` | 绝对误差容忍(单位:换算后的最小单位,通常是"元") |
| `unit_map` | `{}` | 单位文本 → 倍率。例:`{"亿": 100000000, "万元": 10000, "万": 10000, "元": 1}` |

**判定流程**:
1. 用正则 `(-?[\d,]+(?:\.\d+)?)\s*([\u4e00-\u9fffA-Za-z]*)` 从 a/b 中各抽一个**数值+单位**对
2. 单位查 `unit_map` 拿倍率(**最长匹配优先**,避免"万元"被"万"误匹)
3. `|a*倍率 - b*倍率| <= tolerance` 则判 true

**典型示例**(用默认 `unit_map`,`tolerance=0`):

| a | b | 判定 |
| --- | --- | --- |
| `1.2亿` | `12000万元` | ✅ true(都换算为 120 000 000) |
| `1,200,000元` | `120万` | ✅ true |
| `1.2亿` | `1.3亿` | ❌ false(差 1 千万 > 容差) |
| `约 50 万元左右` | `50万` | ✅ true(正则会忽略"约""左右") |
| `不详` | `100万` | ❌ false,reason="无法解析数值" |

**注意点**(留给你审查):
- 当前只抽**第一个**数字。`"投资 200 万元,其中自筹 100 万元"` 会被解析为 200 万 —— 多数情况是对的,但若上游字段值里就是包含多段数字,需要业务侧规范化先。
- `tolerance=0` 在浮点上可能因为换算精度问题失败(如某些极端组合)。若发现"明明一样却判 false",可设 `tolerance: 0.01`。
- 单位倍率是**整数级**的,目前没有支持负数比较或区间比较——如要做"a ≤ b"这类金额范围判定,需要新增一种 type(如 `numeric_compare`)。

### 2.3 `time_order`——日期先后比较

**用途**:批复时间早于申报时间、开工日期晚于立项日期等。

**参数**:

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `operator` | `"lt"` | 比较运算符:`lt`(<) / `le`(≤) / `gt`(>) / `ge`(≥) / `eq`(=) |

**判定流程**:
1. 对 a/b 各调 `parse_date()`,先把 `2024年1月10日` 这种中文日期预处理成 `2024-01-10`,再交给 `dateutil.parser`(`fuzzy=True`)
2. 解析失败任何一边 → `false`,reason 说明哪边失败
3. 否则按 `operator` 比较

**支持的日期写法**:
- `2024-01-10` / `2024/01/10` / `2024.01.10`
- `2024年1月10日` / `2024年01月10日` / `2024年1月10`
- `Jan 10, 2024`、`10/01/2024` 等(由 dateutil 解析)
- **包含混杂文本**也能解析:如 `"于 2024-01-10 批复"`,`fuzzy=True` 会忽略中文部分

**注意点**(留给你审查):
- 比较的是**日期级别**还是**时间级别**:目前默认带时分秒一起比。若 a 是 `2024-01-10`(默认 00:00),b 是 `2024-01-10 14:30`,`operator=lt` 会判 true(因为 0:00 < 14:30)。**业务上是否要"忽略时分秒,只比日期"?**——如需要,要在 `time_order.py` 加一个 `granularity: day` 参数。
- 没有"两个时间相差不超过 N 天"这种容差比较——如有需要也是新 type。

### 2.4 `semantic_similar`——语义"基本一致"(调 LLM)

**用途**:需要"理解意思"的判定。允许措辞差异、简称/全称、行政区划前缀差异、组织形式变体等。

**参数**:

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `strictness` | (无) | 仅作记录,**当前未真正影响判定**——判定逻辑由 `prompt_template` 决定 |

**判定流程**:
1. 渲染 `prompt_template`,把 `{a_value}` / `{b_value}` 替换为真实值
2. 拼上 `app/rules/semantic_similar.py` 里写死的 system prompt(强调"宽松"判定 + 强约束 JSON 输出)
3. 调 LLM 拿到内容,解析 `{"match": ..., "reason": "..."}`
4. 解析失败兜底:用正则 `\{[\s\S]*\}` 提取大括号块再 parse 一次,仍失败则 `match=false, reason="LLM 输出非法 JSON"`

**system_prompt**(写死在 `app/rules/semantic_similar.py:17-24`):

> 你是一位资深的投资项目文件合规审核专家,擅长在两个文本字段之间识别它们是否指向同一事物或语义上"基本一致"。判断标准应当**宽松**:允许措辞差异、简称与全称、有/无前后缀、组织形式变体(如"有限公司"与"有限责任公司")等。只有当两者明显指向不同对象、或关键信息不同时,才判定为不一致。

**注意点**(留给你审查):
- `strictness` 当前是占位字段——**没有任何代码读它**。如果业务上要"loose / normal / strict"三档,需要改 system_prompt 选择逻辑(在 `SemanticRule` 基类里按参数切 prompt)。
- prompt 本质上是产品调参——比如 R004 实测时模型把"贵州省XX建设有限公司"与"XX建设公司"判为**不一致**(认为"未明确为有限公司"),这是模型偏严格,可以在 prompt_template 里加更明确的样例引导。

### 2.5 `semantic_exact`——语义"严格一致"(调 LLM)

**用途**:多个内容项的列表比对,要求**项数不增不减**,允许顺序/标点/格式不同。

**参数**:同 2.4,`strictness` 仅作记录。

**判定流程**:与 `semantic_similar` 一样,但 system_prompt 强调"任一段多/少子项目即判 false":

> 任务:判断两段文本在所列的内容项上是否"**严格一致**"。允许差异:项目顺序、标点符号、空白、序号格式、措辞微调。**不允许**:任一段多出或缺少任何子项目,或子项目的数量/规格不同。

**典型场景**:R005 用它比"建设内容",例如:

| a | b | 期望 |
| --- | --- | --- |
| `1.机房;2.光纤;3.UPS` | `光纤、UPS、机房` | ✅ true(顺序/分隔符不影响) |
| `1.机房;2.光纤` | `1.机房;2.光纤;3.UPS` | ❌ false(b 多一项) |
| `机房改造` | `机房新建` | ❌ false(规格不同) |

## 3. 当前 5 条规则(R001-R005)逐条解读

| ID | 名称 | 类型 | 字段 A | 字段 B | 判定 | 是否调 LLM |
| --- | --- | --- | --- | --- | --- | --- |
| R001 | 项目代码完全一致 | `exact_match` | 项目代码 | 项目代码 | 归一化后必须完全相同 | ❌ |
| R002 | 总投资金额一致 | `numeric_equal` | 总投资 | 总投资金额 | 数值相等(支持亿/万元换算) | ❌ |
| R003 | 批复时间早于申报时间 | `time_order` | 批复时间 | 申报时间 | a 严格早于 b (`lt`) | ❌ |
| R004 | 建设单位名称基本一致 | `semantic_similar` | 建设单位 | 建设单位 | 同一法人主体(宽松) | ✅ |
| R005 | 建设内容详情完全一致 | `semantic_exact` | 建设内容 | 建设内容 | 内容项一一对应(严格) | ✅ |

**需要业务侧确认的几点(很重要)**:

1. **R003 的"批复时间早于申报时间"——业务上真是这个方向吗?**
   通常实务里,**先有申报、后有批复**,所以"批复时间应该 ≥ 申报时间"才对。当前规则写的是 `lt`(批复早于申报)——这看起来像是反过来,需要你确认是不是占位演示,正式版要不要改成 `gt` 或 `ge`?

2. **R002 默认 `tolerance=0.0`**——金额完全相等才判 true。
   实务里两份文件经常出现"四舍五入差几分钱"或"一份写 1.2 亿、一份写 12000.00 万元"(0 误差通过),但若涉及人民币精确金额(如 1234567.89 元 vs 1234567.9 元),`tolerance=0` 就会判 false。需不需要默认放宽 1 元/100 元?

3. **R004 / R005 的 `strictness` 字段当前没生效**——只是占位记录。如果你需要"宽松/正常/严格"三档切换,告诉我,我加一层 prompt 选择逻辑。

4. **`expected_field_names` 是软提醒,目前未生效校验**——上游传 `field_a.name="建设单位"` 而规则配的是 `["建设单位", "建设单位"]`,系统**不会**因为名字不对而拒绝。如果需要硬校验,我可以加。

   注:这与 `require_field_name` 不同——后者只校验 name **是否提供**,不校验内容是否匹配 yaml 里写的字符串。

5. **5 条规则只覆盖 5 种类型,数量上对应"7-8 条规则"的初始目标还差 2-3 条**——你最近提到 5 类文件:可研批复、初设批复、项目纳入实施方案说明、削绩情况说明、地方财政资金承诺函。这些文件之间还要查哪些字段?常见可能补充:
   - 建设地点(`semantic_similar`)
   - 项目代号/编号交叉一致性(`exact_match`)
   - 建设规模/工期(`numeric_equal` 或 `semantic_similar`)
   - 资金来源结构(`semantic_exact`)
   - 削绩比例阈值(可能需要新类型 `numeric_compare`,比"等于"多支持区间)

## 4. 字段名/规则 ID 命名规范建议

- **规则 ID**:`R001`、`R002`……三位数字,留 1000 条扩展空间。**不要复用**已经退役的 ID(下游可能还在缓存)。
- **`name`**:简短中文短语,**用作日志/前端显示**——尽量带上"什么 × 关系"(如"批复时间×申报时间一致")。
- **`description`**:面向后续维护者的"为什么这么写",可以写较详细。
- **`expected_field_names`**:严格用业务字段中文名,与第一阶段 VLM 抽取的字段名保持一致。

## 5. 如何添加/修改规则

### 5.1 复用已有 type(最常见)

直接在 `rules.yaml` 加一条,改 `id`/`name`/`params`/`prompt_template` 即可。保存后下次请求自动生效。

### 5.2 需要新的 type(如金额范围、相差天数)

5 步法,详见 [`docs/development/README.md`](../development/README.md) 的"如何添加一条规则"章节。本人/开发同学操作:
1. 判断要不要调 LLM(能 Python 算就别调)
2. 新建 `app/rules/<type_name>.py`,实现 `Rule.compare()`
3. 在 `app/rules/__init__.py` 加 import
4. 加单元测试
5. 在 `rules.yaml` 加规则项
