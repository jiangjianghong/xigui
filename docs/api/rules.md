# 规则配置详解(`config/rules.yaml`)

> 本文档面向**业务/产品/审核同学**——目标是让你看完之后能:
> 1. 理解每一条规则在判什么、prompt 如何调
> 2. 评估初始版本(R001-R005)是否贴合实际业务
> 3. 自行复制粘贴一条已有规则,改 id + prompt 就快速构建新规则

---

## 1. 设计原则:全规则走 LLM

本服务**所有规则都通过 LLM 判定**,不再有"确定性 vs 语义"之分。

为什么这么做:
- 规则边界经常变,业务侧描述清楚比让开发硬编码 Python 实现更灵活
- 容差、单位换算、日期解析、模糊匹配,所有"判定标准"都在 prompt 里用中文描述,改 prompt 不改代码
- 复制一条规则 → 改 id + 改 prompt = 新规则上线,无需开发介入

代价(项目经理已认可):
- 每次请求都有 LLM 调用成本(走内网 vLLM 时基本不计)
- 同一输入两次跑结果可能微小波动(合规审计场景接受)
- 解析数值/日期等场景的可靠性取决于 prompt 写得是否清楚

## 2. 整体结构

`config/rules.yaml` 是**活配置**——保存即生效:

- **自动**:下一次 `/compare` 请求时,系统会基于文件 mtime 自动重新加载
- **手动**:`curl -X POST http://localhost:6549/admin/reload-rules`

文件根节点为 `rules:`,下面是若干条规则。每条规则的字段:

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `id` | ✅ | 规则唯一编号(如 `R001`),**上游调 `/compare` 时按这个 id 找规则** |
| `name` | ⭕ | 中文规则名(用于日志、对外展示) |
| `description` | ⭕ | 规则描述,仅用于日志/文档,不影响判定 |
| `field_defs` | ⭕ | 字符串数组。字段定义列表,**下标即 `{field_N}` 占位符下标**,元素为字段业务名。供管理 UI 生成配置 chip 与试跑页输入框标签;`/compare` 运行时不读取,不影响判定 |
| `require_field_name` | ⭕ | bool。该规则下请求里各字段的 `name` 是否必填(详见 §3) |
| `system_prompt` | ⭕ | LLM 系统提示。建议每条规则按自身领域显式声明;留空(空字符串)则不向模型发送 system 消息(详见 §4.4) |
| `prompt_template` | ✅ | **规则的核心**——用自然语言描述判定标准。占位符见 §4 |

## 3. `require_field_name` 与字段名注入

接口请求里 `fields` 是一个数组,每个元素各有 `name`(字段名)和 `value`(字段值):

```json
{ "fields": [{"name": "建设单位", "value": "贵州省XX建设有限公司"}, ...] }
```

- `value` **永远必填**(Pydantic 层校验,缺则 422)
- `name` 是否必填,完全看 yaml 里该规则**显式声明**的 `require_field_name`:

| `require_field_name` | 行为 |
| --- | --- |
| `true` | 上游必须传各字段的 `name`,缺则返 422 |
| `false` | 不校验 name,可省略 |
| 未配置 | 等价于 `false`,但**建议每条规则都显式写出来**(便于审阅) |

**未提供 name 时的 422 响应**:`{"detail":"rule R004 要求字段 name 必填"}`

### 3.1 何时设为 `true`

**只要 `prompt_template` 引用了 `{field_0_name}` 或 `{field_1_name}`,就必须设 `true`**——否则 LLM 拿到的会是空字符串,prompt 上下文丢失,判定不准。

```yaml
- id: "R004"
  require_field_name: true   # 因为下面 prompt_template 用了 {field_0_name}/{field_1_name}
  prompt_template: |
    请判断字段"{field_0_name}"与字段"{field_1_name}"的两个值是否指向同一主体。
    A: {field_0}
    B: {field_1}
    ...
```

### 3.2 何时设为 `false`

普通规则,prompt 里没有用到 `{field_0_name}` / `{field_1_name}`,name 是否传都不影响判定:

```yaml
- id: "R001"
  require_field_name: false  # prompt 没用 {field_0_name},name 可省略
  prompt_template: |
    判断两个项目代码是否一致。
    A: {field_0}
    B: {field_1}
    ...
```

## 4. `prompt_template` 编写指南

### 4.1 支持的占位符

| 占位符 | 来源 | 说明 |
| --- | --- | --- |
| `{field_0}` | 请求 `fields[0].value` | **总是有值**(Pydantic 强制) |
| `{field_1}` | 请求 `fields[1].value` | 同上 |
| `{field_0_name}` | 请求 `fields[0].name` | 用了它就触发 `require_field_name=true` |
| `{field_1_name}` | 请求 `fields[1].name` | 同上 |

### 4.2 必须严格输出 JSON

模板末尾**务必**让 LLM 输出固定结构:

```
严格按 JSON 输出,不要任何额外说明:
{{"match": true|false, "reason": "<不超过30字的中文理由>"}}
```

注意 YAML 里 JSON 的大括号要写成**双重 `{{ }}`**,否则 Python `.format()` 会把 `{...}` 当成占位符报错。

服务端解析逻辑:
1. 先 `json.loads` 严格解析
2. 失败用正则 `\{[\s\S]*\}` 提取第一个大括号块再解析
3. 还失败则 `match=false, reason="LLM 输出非法 JSON"`(成本仍计)

### 4.3 写好 prompt 的几个要点

- **明确允许差异 vs 不允许差异**:列清楚两边。例如金额比对要写"允许:单位差异、千分位逗号;不允许:任何实际数值差异"
- **给关键示例**:若边界容易出错,在 prompt 里举 1-2 个正反例(few-shot)
- **要求 reason 长度**:"不超过 30 字" 能控制输出稳定性
- **不要写"如有疑问可询问"**:LLM 不会真问你,只会编理由
- **复杂规则可拆**:一条 prompt 只判一件事,不要塞多个判定标准

### 4.4 system_prompt(每条规则按领域显式声明)

每条规则可以指定 LLM 的 system 角色提示。**建议每条规则都显式声明**——不同业务字段对应的"专家身份"不同,把这件事下放到 yaml 比硬编码默认值更灵活。

- **显式声明**:`system_prompt: "你是熟悉企业法人主体识别的合规审核员..."` → LLM 调用时会插入一条 `{"role": "system", "content": "..."}` 消息
- **留空 / 不写**:不向模型发送 system 消息,只发 user 消息——适用于完全用 `prompt_template` 自洽表达任务的极简场景

不同场景的写法示例:

```yaml
- id: "R002"
  system_prompt: "你是熟悉政府投资项目财务管理的注册会计师,擅长金额单位换算(亿/万/元)与一致性核对。"
  prompt_template: |
    ...

- id: "R020"
  system_prompt: "你是熟悉政府投资项目法律事务的法律顾问。"
  prompt_template: |
    ...
```

> 注:旧版本曾内置过一个"合规审核专家"默认值,现已移除——避免不同领域的规则共用同一个不太贴切的身份。

## 5. 当前 5 条规则(R001-R005)逐条解读

| ID | 名称 | 字段 A | 字段 B |
| --- | --- | --- | --- |
| R001 | 项目代码完全一致 | 项目代码 | 项目代码 |
| R002 | 总投资金额一致 | 总投资 | 总投资金额 |
| R003 | 批复时间早于申报时间 | 批复时间 | 申报时间 |
| R004 | 建设单位名称基本一致(用了 `{field_0_name}/{field_1_name}`) | 建设单位 | 建设单位 |
| R005 | 建设内容详情完全一致 | 建设内容 | 建设内容 |

**需要业务侧确认的几点(很重要)**:

1. **R003 的"批复时间早于申报时间"——业务上真是这个方向吗?**
   通常实务里**先有申报、后有批复**,所以应该是 `批复时间 >= 申报时间` 才对。当前 R005 prompt 写的是"A 严格早于 B"——这看起来像是反过来,需你确认是不是要改方向。

2. **R002 的金额比对**:当前 prompt 写明"任何数值差异即不一致"。若实务里需要容忍"四舍五入差几分钱"或"申报四舍五入到万元",请在 prompt 里加上"允许 X 元以内的差异"。

3. **R001 容忍范围**:当前允许首尾空白、大小写、全半角差异。若业务要求"项目代码必须一模一样,连大小写空白都不能差",在 prompt 里改成"不允许任何字符差异"即可。

4. **5 条规则只覆盖 5 种典型场景**,实际业务还需补充:
   - 建设地点
   - 项目代号/编号交叉一致性
   - 建设规模/工期
   - 资金来源结构
   - 削绩比例阈值
   - ……请补充你想到的字段

## 6. 字段名/规则 ID 命名规范建议

- **规则 ID**:`R001`、`R002`……三位数字,留 1000 条扩展空间。**不要复用**已经退役的 ID(下游可能还在缓存)
- **`name`**:简短中文短语,用作日志/前端显示——尽量带上"什么 × 关系"(如"批复时间×申报时间一致")
- **`description`**:面向后续维护者的"为什么这么写",可以写较详细

## 7. 如何添加/修改一条规则

**完全不需要改代码**。流程:

1. 打开 `config/rules.yaml`
2. 复制一条已有规则
3. 改 `id`(必须唯一)、`name`、`description`、`prompt_template`
4. 保存
5. 下次 `/compare` 请求自动生效;或手动调 `POST /admin/reload-rules` 立刻刷新

例如新增"R006 建设地点基本一致":

```yaml
- id: "R006"
  name: "建设地点基本一致"
  description: "判断两个建设地点描述是否指向同一位置"
  prompt_template: |
    请判断以下两个"建设地点"描述是否指向同一位置。
    允许差异:行政区划层级写法(如"贵州省贵阳市" 与 "贵阳市")、
    详略不同(如"贵阳市南明区XX路 88 号" 与 "贵阳市南明区")。
    不允许差异:省份/城市/区县任一级别不同。
    A: {field_0}
    B: {field_1}
    严格按 JSON 输出:
    {{"match": true|false, "reason": "<不超过30字的中文理由>"}}
```
